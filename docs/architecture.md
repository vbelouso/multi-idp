# What We Build

The lab has two independent authorization domains. Each Keycloak installation has its own namespace, PostgreSQL database, realm, signing keys, and generated credentials.

## Components

The deployed components have fixed roles in the PoC.

| Component | Location | Responsibility |
| --- | --- | --- |
| Internal Keycloak and PostgreSQL | `multi-idp-internal`, realm `internal` | Accept the approved RH assertion and issue internal tokens |
| Agent A | `multi-idp-internal` | Obtain tokens, call C and B, and return results |
| Agent C | `multi-idp-internal` | Process an A2A request authorized by Internal Keycloak |
| External Keycloak and PostgreSQL | `multi-idp-external`, realm `partner` | Accept the internal assertion and issue external authority |
| Agent B | `multi-idp-external` | Process an A2A request authorized by External Keycloak |
| Bootstrap Job | One per namespace | Establish approved identity links and protected attributes |
| Acceptance runner | Local workstation | Invoke A, correlate evidence, and run isolated regression probes |

The [Keycloak manifests](../manifests/internal-keycloak.yaml) and [external counterpart](../manifests/external-keycloak.yaml) use standalone RHBK containers with realm import, PostgreSQL StatefulSets, persistent storage, and HTTPS routes. The configured features include JWT Authorization Grant and Standard Token Exchange V2.

The [agent manifests](../manifests/agents.yaml) run the Python A2A SDK applications. Agent code and pinned dependency requirements are delivered through ConfigMaps generated by [Kustomize](../kustomization.yaml). Each agent installs its dependencies in an init container and exposes an HTTPS Agent Card and A2A endpoint.

## Realm Registrations

OAuth registrations describe callers and recipients independently of the deployed applications.

| Registration | Realm | Purpose |
| --- | --- | --- |
| `agent-a-internal` | Internal | A's authenticated client for the RH grant and internal exchanges |
| `agent-c` | Internal | Audience for calls to C |
| External realm issuer URL | Internal | Audience target for the assertion sent to External Keycloak |
| `agent-a-external` | External | A's authenticated client for the external JWT grant |
| `agent-b` | External | Audience for calls to B |
| `unapproved-agent` | Both | Negative-test fixture for client authorization checks |
| `realm-provisioner` | Both | Administrative setup and test inspection |

Client scopes `c.invoke` and `partner.invoke` carry the intended authority. The agents require the corresponding permissions `invoke-c` and `invoke-b`. Definitions are in the [internal realm](../realms/internal.json) and [external realm](../realms/external.json).

## Administrative Setup

[deploy.sh](../deploy.sh) generates namespace-local Secrets and applies the manifests. On an empty database, Keycloak imports the realm and creates the initial `console-admin` account in the master realm using its bootstrap environment variables.

The [bootstrap Job](../manifests/bootstrap.yaml) runs [bootstrap.sh](../realms/bootstrap.sh) with the bundled `kcadm.sh`. It establishes the following mappings:

```text
Approved RH issuer and subject
    -> Internal pilot user
    -> External pilot user
```

The RH subject comes from the explicitly approved local file. Bootstrap also sets `origin_issuer`, `origin_sub`, `internal_sub`, and `provenance_version` as protected attributes. It rejects conflicting existing links or protected values.

Agent A receives its two OAuth client secrets. Its ServiceAccount does not mount a Kubernetes API token, and its application does not use Keycloak Admin APIs. Agent B validates signed token claims without a runner-generated provenance Secret.

Refer to [the runtime flow](flow.md) for the exchanges and [identity concepts](concepts.md#approved-identity-and-provenance) for the approval and trust boundaries.
